# SegueEMR - Project Feature & Architecture Summary

This document provides a comprehensive overview of the SegueEMR project, detailing its architecture, tech stack, and full feature set. It is designed to be provided to an AI model to explain the project in detail.

## 1. Project Overview & Architecture
SegueEMR is a unified Electronic Medical Records (EMR) and practice management platform. The system facilitates end-to-end healthcare workflows covering patient registration, clinical encounters, lab processing, and pharmacy dispensing.

**Architectural Paradigm:**
* **Database (System of Record):** PostgreSQL, accessed via Prisma ORM. Replaces legacy blockchain immutability with relational consistency.
* **Storage:** Azure Blob Storage for EHR file uploads with client-side **AES-256-CBC encryption**.
* **Interoperability (SMART-on-FHIR):** Asynchronous, best-effort syncing of clinical data (Appointments, Prescriptions, Lab Orders) to a FHIR server.
* **Directory Sync:** Microsoft Dataverse integration for syncing `users`, `patients`, and `doctors` to CRM entities.
* **Deployment:** Docker & Docker Compose support for containerized deployment of the full stack (Frontend, Backend, DB).

## 2. Technology Stack
### Backend
* **Runtime:** Node.js v18+
* **Framework:** Express.js (REST API)
* **ORM:** Prisma (`@prisma/client`)
* **Database:** PostgreSQL
* **Authentication:** JWT (`jsonwebtoken`), bcrypt for hashing. *Note: Custom demo bypass exists for presentation purposes.*
* **Storage SDK:** `@azure/storage-blob`
* **Other Utilities:** Multer (file handling), compression, helmet, cors, winston (logging).
* **Testing:** Jest, Supertest.

### Frontend
* **Framework:** Next.js 16.2.11 (React 19)
* **Styling:** TailwindCSS v4
* **Language:** TypeScript
* **HTTP Client:** Axios
* **Icons:** Lucide React
* **Testing:** Playwright (End-to-End UI testing).

## 3. Supported Roles & Access Levels
* **Patient:** Upload/view own records, manage doctor access, update intake details.
* **Doctor:** View patient records, write clinical notes (SOAP), issue prescriptions, order lab tests, manage appointments.
* **Nurse:** Patient check-in, record vitals, update appointment statuses.
* **Receptionist:** Schedule/reschedule appointments, manage patient registration, generate invoices.
* **Lab Technician:** Process multi-tenant lab orders, upload PDF results.
* **Pharmacist:** View and dispense prescriptions in dedicated queues.
* **Administrative Staff:** User management, system oversight, audit logs.
* **Healthcare Management:** Analytics dashboard.

## 4. Core Features & Functionalities (Based on Database Schema)

### 4.1. Patient & User Management
* **Demographics & Intake:** Extensive tracking of patient details (`patient_intakes`), including marital status, insurance provider, HIPAA consent, and emergency contacts.
* **Intake Auditing:** Detailed change tracking via `patient_intake_audit_logs`.
* **API Keys:** Patients can generate API keys (`PatientApiKey`) for programmatic access to their own data.
* **Patient Forms:** Dynamic forms tracking (`PatientForm`) for custom questionnaires.

### 4.2. Clinical Workflows
* **Appointments:** Scheduling system linking Patients and Doctors.
* **Clinical Notes (SOAP):** Doctors record encounters using the Subjective, Objective, Assessment, and Plan format.
* **Extended Charting:** Additional chart capabilities for Office Notes, Patient Education materials, Authorizations, and real-time Eligibility Checks.
* **Vitals Tracking:** Logging of temperature, blood pressure, pulse, and SpO2 per appointment.
* **Allergies & Problems:** Structured tracking of patient allergies (severity/reaction) and clinical problems (onset date/description).

### 4.3. Prescriptions & Pharmacy
* **Prescription Management:** Doctors issue prescriptions with attached diagnoses.
* **Medications:** Line items per prescription detailing name, dosage, frequency, and duration.
* **Dispensing & Refills:** Tracking which pharmacy/pharmacist dispensed the medicine and when. A dedicated `MedicationRefill` table manages refill requests.

### 4.4. Laboratory & Diagnostics
* **Lab Orders:** Tracked by test name, priority (critical flag), result summaries, and processing technician.
* **Result Uploads:** Results are uploaded as PDFs to Azure Blob Storage (`pdfBlobUrl`, `pdfBlobName`).
* **Lab Audits:** Every action taken on a lab order is logged in `LabAudit` for compliance.

### 4.5. Billing & Invoicing
* **Invoices:** Generated by receptionists, tracking total amounts and payment statuses (e.g., unpaid/paid).
* **Line Items:** Granular breakdown of charges within an invoice.

### 4.6. System & Infrastructure
* **Activity Logs:** System-wide audit trail (`ActivityLog`) tracking user actions for security and compliance.
* **Notifications:** Internal alerting system (`Notification`) triggered by various events (e.g., lab result completed).
* **Messaging:** Real-time internal communication channel (`Message`) between patients and staff powered by WebSockets (`socket.io`), featuring instant delivery and cross-session identity consistency.
* **EHR Metadata:** Tracks encrypted file uploads in Blob Storage and maps them to standard FHIR Resources.
* **Recalls:** System for scheduling patient follow-ups or reminders (`Recall`).
* **Settings:** Global system configuration key-value store.

## 5. Notable Quirks & Demo Configurations
* **Demo Authentication:** A backend override allows bypassing standard auth by using the password `demo`. This populates mock data and ensures smooth workflows during presentations.
* **Graceful Degradation:** The Blob Storage and FHIR integration services are designed to fail silently or return mock data (e.g., mock PDF blobs) if the external services or emulators (like Azurite) are offline, preventing demo crashes.
